## Supabase email sign-in

1. The additive launch migration is already installed on WoffNote Share; do not apply it again. For a new isolated environment, prepare its reviewed baseline and confirm account, merge-ticket, billing-ledger and admission RPC permissions: browser roles cannot write entitlements or call `process_billing_event`/`record_sender_checkout`.
2. Keep anonymous sign-in enabled and enable manual identity linking. Keep email confirmation enabled. Configure production SMTP, verified sender domain, email rate limits and delivery monitoring. Verify actual delivery and account flows before setting `WOFF_EMAIL_DELIVERY_VERIFIED=true`. The current controlled delivery test used Gmail; check additional mailbox providers as the audience grows.
3. Set `NEXT_PUBLIC_SITE_URL` to the exact canonical HTTPS origin. Add that origin's `/auth/callback` URL to the Supabase redirect allowlist. Avoid broad production wildcards.
4. The normal confirmation redirect uses PKCE `/auth/callback`. For links that work across devices and avoid email scanners consuming tokens, use an explicit confirmation page in the email templates. Magic link template link: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email&next=/dashboard`. Email Change template link: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email_change&next=/dashboard`. Test the anonymous conversion template separately; the old email value can be empty. The page requires a deliberate POST to verify the token.
5. Test guest-to-new-account conversion: the UID and owned rooms must stay the same. Test existing-account sign-in from a browser containing guest rooms: the 10-minute, single-use proof must transfer only source-owned rooms and source-authored content within those rooms. Billing identity never transfers. Before the merge succeeds, the callback buffers target auth cookies, preserving the guest cookies on failure. An expired proof requires a fresh link from the original browser. A new browser can sign in without transferring another browser's rooms. A browser that already owns rooms cannot switch to a different account without its own initiating transfer proof; source-session or ownership lookup failures stop before cookie replacement.
6. Exercise expired links, email conflicts, resend rate limits, a callback failure, a merge failure and sign-out. Confirm private auth/account paths are excluded from indexing, shared caching and analytics. Email verification establishes possession of the address; operators must not turn on Supabase auto-confirm.

## Lemon Squeezy

Merchant approval and Bangladesh payout verification are requirements for eventual Live sales. Country eligibility is separate from account approval and a successful payout. The owner can leave activation pending for this Test release; the provider portal will remain unavailable until activation is approved.

Configure a single **USD $8 monthly** subscription variant, without a trial, setup fee or usage charges. Use the provider's standard `*.lemonsqueezy.com` hosted checkout and portal domain; custom provider domains are not enabled by this implementation. Only this server-configured variant is offered. Checkout rechecks the latest Price object and store currency. Do not publish a separate reusable product buy-link: purchases must start from the signed-in Woff checkout so the reservation and signed ownership binding are attached.

Server-only variables:

| Variable | Purpose |
| --- | --- |
| `LEMON_SQUEEZY_API_KEY` | API access for hosted checkout, portal and reconciliation |
| `LEMON_SQUEEZY_STORE_ID` | The configured store ID; current Test store 492282 |
| `LEMON_SQUEEZY_VARIANT_ID` | The single monthly Pro variant ID |
| `LEMON_SQUEEZY_WEBHOOK_SECRET` | Raw-body HMAC verification and checkout ownership binding; keep stable or coordinate rotation of outstanding checkouts |
| `LEMON_SQUEEZY_TEST_MODE` | `true` for the current public no-charge release; `false` only for a separately authorized Live switch |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only billing ledger writes, never exposed in client code |

Application gates: verified accounts, verified email delivery, configured provider credentials and `WOFF_BILLING_ENABLED=true` are required for Test checkout. Live checkout additionally requires `WOFF_STORAGE_CAPACITY_VERIFIED=true`; the current Test release keeps that Live-capacity flag false. The database admission gate and payment mode must also agree. Existing subscriptions retain their management route when checkout is paused, subject to the provider's activation restriction. Do not disable accounts to pause new checkout.

Configure the webhook at `https://<canonical-host>/api/billing/webhook` for all supported subscription state and invoice events: created, updated, cancelled, resumed, expired, paused, unpaused, payment success, payment failed, payment recovered and payment refunded. Compare the exact event names in `lib/billing/helpers.ts`. HMAC uses the unmodified UTF-8 request body. Unsupported events are acknowledged without entitlements. Invalid signatures are rejected. Reconciliation failures return non-2xx for retry; provider retries are finite, so monitor failures and replay from the provider dashboard after repair.

Each event re-reads the current subscription and its newest invoice. The provider documents invoice lists as descending by `created_at`. A full refund of the newest invoice stops new Pro access; a historical refund cannot override a newer paid period, and a partial refund retains the paid period. Refunds do not automatically cancel future provider charges in this implementation: an operator must cancel/adjust the subscription in the provider when appropriate and confirm the portal reflects that decision. Reconciliation also verifies store, variant, customer, subscription and test/live mode. A signed custom user ID and checkout reservation are required for initial subscription binding. No query parameter or checkout-return page grants access.

Customers review the offer at `/checkout`. `POST /api/billing/checkout` creates or reuses their hosted checkout after verified account and capacity checks. The hosted checkout return and receipt link use `/checkout/complete`, which reads `GET /api/billing/status` for up to 60 seconds and offers a manual status check if confirmation is delayed. An elapsed cancelled paid period shows ended access rather than waiting for confirmation; that presentation was checked with a synthetic clock. The status endpoint exposes only the verified requester's entitlement presentation and uses private, no-store responses. `POST /api/billing/portal` opens management for the attached provider customer, subject to provider store activation. Existing renewable subscriptions use the portal; a fully ended subscription can start a fresh purchase only when it holds no paid access or renewable capacity reservation.

## Capacity and launch admission

The database `woff_private.pilot_capacity` row defaults to closed admission and zero capacity. The current public Test release retains the conservative **800 MiB shared physical upload budget**, with Test-mode admission and mode provenance on entitlements/reservations. Server `LEMON_SQUEEZY_TEST_MODE` and database `billing_test_mode` must match. A record with unknown or different mode cannot grant Pro; Test-origin accounts normalize to Free after a Live switch. Retaining the same backend does not convert simulated purchases into Live subscriptions.

Capacity accounting always charges physical objects, including expired/deleted objects awaiting cleanup, plus pending uploads. Test subscriptions exercise Pro controls within this shared limit and reserve zero unused paid-storage allowance. They cannot bypass upload admission. Live active/pending/renewable commitments still reserve the unused part of the full **1 GiB** allowance, including `billing_capacity_reserved` commitments while payment can renew/retry/resume. The current 800 MiB budget cannot support a Live allowance; verify sufficient actual capacity and headroom before opening Live checkout. A configuration flag does not provision storage.

Admission atomically limits active/pending/renewable senders in the configured payment mode. A 30-minute reservation expires with the hosted checkout and retains its mode. Repeat requests reuse the recorded URL, and concurrent preparation is blocked. Provider timeouts retain the reservation because a checkout might already exist. The public release RPC cannot delete an issued payable reservation. Late activation rechecks admission; Live activation also rechecks the full storage commitment. Monitor reservations and failed callbacks; account status becomes Pro only after verified reconciliation succeeds.

Access uses bounded provider paid-through dates. Cancellation keeps Pro through the paid deadline; a failed renewal has at most three days of grace anchored to the previous paid-through date, never to another retry's `renews_at`. Trial, pause, expiry, non-payment and latest full refund do not grant new Pro actions. Existing rooms retain their fixed expiry; billing does not rewrite room deadlines. Downgrade does not delete files early. If the account is over the Free allowance, new uploads are blocked until usage is lower; existing paid room deadlines still apply.

## Pause and Live switch

Pause new checkout with `WOFF_BILLING_ENABLED=false` and `pilot_capacity.checkout_enabled=false`, redeploy, and retain account access, signed reconciliation and cleanup. Closing admission does not cancel subscriptions.

When separately authorized, pause first and resolve outstanding Test checkouts/subscriptions before supplying distinct Live provider credentials and webhook. Change both payment modes to false, verify sufficient physical capacity, then reopen admission and deploy. Test-origin entitlement records remain auditable and normalize to Free in Live mode; they do not grant paid controls, occupy Live admission slots or become Live subscriptions. Do not delete customer files or reuse Test provider IDs as part of the switch.

Local checks: `npm run test:unit`; TypeScript/lint/build; local SQL fixture checks. These do not replace real SMTP delivery or a real provider test-mode checkout and webhook. No new cloud environment is required for those provider checks.
